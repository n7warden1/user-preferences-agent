# Ассистент с долговременной памятью предпочтений

Компактный backend-сервис для тестового задания: FastAPI передаёт сообщение LLM-агенту,
агент самостоятельно решает, нужно ли вызвать инструменты памяти, а предпочтения хранятся
в файловой SQLite между перезапусками.

## Стек

- Python 3.11+
- FastAPI и Pydantic
- LangChain `create_agent` (агентный цикл на LangGraph)
- `langchain-ollama` / `ChatOllama`
- локальная модель Ollama `qwen3:14b`
- SQLite
- pytest и HTTPX (через `TestClient` FastAPI)

## Архитектура

```text
POST /chat
    │  ChatRequest: user_id + message
    ▼
FastAPI ── server context(user_id, storage) ──► LangGraph agent
                                                   │
                                      LLM выбирает │ инструмент
                                  ┌────────────────┴────────────────┐
                                  ▼                                 ▼
                         get_preferences                    save_preference
                                  └────────────────┬────────────────┘
                                                   ▼
                                     SQLite preferences.db
                                  PK (user_id, category)
```

HTTP-слой не читает и не записывает предпочтения. `user_id` попадает в инструменты через
типизированный `ToolRuntime` и отсутствует в JSON-схемах, доступных модели. `create_agent`
повторяет цикл «модель → инструмент → модель» до финального ответа, поэтому поддерживаются
несколько последовательных вызовов в одном запросе.

### Семантические категории

В SQLite действует уникальность `(user_id, category)` и атомарный `UPSERT`. Системная
инструкция требует перед записью получить текущую память, выбрать короткую стабильную
категорию в `snake_case` и повторно использовать семантически равнозначную категорию.
Например, новое значение `drink` заменит старое, а `color` останется отдельной записью.
Pydantic ограничивает синтаксис категории, но смысловое сопоставление выполняет LLM,
а не набор `if/else` или регулярных выражений.

## Установка в Windows PowerShell

Требуются Python 3.11+ и установленный [Ollama](https://ollama.com/download/windows).

```powershell
# Выполняйте команды из корня распакованного или клонированного проекта.
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
Copy-Item .env.example .env
ollama pull qwen3:14b
```

Если PowerShell запрещает активацию, команды можно выполнять напрямую через
`.\.venv\Scripts\python.exe`.

## Конфигурация

Пример `.env`:

```dotenv
OLLAMA_MODEL=qwen3:14b
OLLAMA_BASE_URL=http://localhost:11434
OLLAMA_TIMEOUT_SECONDS=120
SQLITE_PATH=data/preferences.db
AGENT_RECURSION_LIMIT=12
```

`OLLAMA_TIMEOUT_SECONDS` ограничивает весь запрос к агенту и сетевой клиент Ollama.
`AGENT_RECURSION_LIMIT` защищает от бесконечного цикла вызовов инструментов. Для Qwen3
включён документированный режим `reasoning=False`: внутренние рассуждения не возвращаются
через API, а tool calling остаётся доступен.

## Запуск

Убедитесь, что Ollama запущен, затем:

```powershell
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Примеры запросов:

```powershell
$body = @{ user_id = "alice"; message = "Я предпочитаю чай" } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8000/chat" `
  -ContentType "application/json" -Body $body

$body = @{ user_id = "alice"; message = "Какой напиток мне посоветуешь?" } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8000/chat" `
  -ContentType "application/json" -Body $body

$body = @{ user_id = "alice"; message = "Теперь предпочитаю кофе" } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8000/chat" `
  -ContentType "application/json" -Body $body
```

Ответ имеет вид:

```json
{"response": "Запомнил: теперь вы предпочитаете кофе."}
```

## Тесты и проверки

Автоматические тесты не обращаются к Ollama, интернету или платным API. В них используется
детерминированная `BaseChatModel`, которая формирует настоящие tool calls; вызовы выполняет
реальный граф, а тесты проверяют `ToolMessage` и содержимое SQLite.

```powershell
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
```

Покрыты: новая запись, чтение через инструмент, обновление, отсутствие дубликатов,
изоляция пользователей, prompt injection с запросом чужой памяти, сохранность после
повторного создания приложения, валидация HTTP, ошибка LLM, последовательный агентный
маршрут, попытка передать чужой `user_id` в аргументах инструмента, некорректные аргументы,
немаскируемая последующим успешным вызовом ошибка инструмента, полный HTTP-цикл обновления
`drink` без дубля, независимость категорий `drink` и `color`, сбой SQLite и параллельные
записи разных пользователей.

Отдельно выполнена ручная интеграционная проверка с Ollama 0.40.18 и реальной
`qwen3:14b` (`Q4_K_M`) на RTX 4070 Ti SUPER. Она подтвердила реальные вызовы инструментов,
обновление `drink: tea → coffee`, отсутствие дубликатов и синонимичных категорий,
сохранность отдельного `color`, изоляцию пользователей, защиту от запроса чужой памяти и
чтение той же SQLite-базы после запуска нового Python-процесса. Временные LLM-сценарии и
их тестовые базы удалены; основной набор pytest по-прежнему не требует Ollama.

Фактический локальный результат проверок приведён в конце README.

## Изоляция и безопасность

- Модель видит у `save_preference` только `category` и `value`, а у `get_preferences` —
  пустой набор аргументов.
- `user_id` задаётся HTTP-запросом и внедряется сервером в неизменяемый контекст каждого
  запуска. Глобальной переменной текущего пользователя и общего SQLite-соединения нет.
- Каждый запрос к SQLite параметризован; на операцию создаётся отдельное соединение.
- Ошибки инструментов и хранилища проверяются перед возвратом финального текста, поэтому
  сбой записи не превращается в ложное сообщение об успехе.
- Клиенту не возвращаются трассировки, пути к файлам и внутренние ошибки провайдера.

Важно: `user_id` обеспечивает логическое разделение данных, но сервис намеренно не имеет
аутентификации по условиям задания. В реальной системе клиент может подменить `user_id`;
идентификатор следует брать из проверенного токена или серверной сессии.

## Решения и сознательные упрощения

- Полная история диалога и LangGraph checkpointer не хранятся: долговременная память здесь
  состоит только из предпочтений и доступна через два требуемых инструмента.
- Нет словаря всех возможных категорий: семантику определяет модель с учётом уже сохранённых
  значений. Это сохраняет обобщаемость, но требует интеграционной оценки выбранной LLM.
- SQLite работает в WAL-режиме; атомарный `UPSERT` и первичный ключ предотвращают дубликаты.
- Нет повторных запросов к LLM: при недоступности возвращается `503`, при тайм-ауте `504`,
  при некорректном ответе или исчерпании шагов — `502`, а при неожиданной внутренней
  ошибке — безопасный `500` без деталей исключения.
- Не добавлены Docker, авторизация, RAG, векторная БД, Redis, мониторинг и CI/CD.

## Известные ограничения

- Качество объединения синонимичных категорий зависит от Qwen3 и системной инструкции.
- Для одного HTTP-запроса нет идемпотентного ключа: клиентский повтор после сетевого обрыва
  снова запустит агента, хотя `UPSERT` не создаст дубль одной категории.
- SQLite подходит для одного небольшого сервиса; при высокой распределённой нагрузке нужно
  другое хранилище.
- Семантическое сопоставление всё равно зависит от версии и квантизации модели. Проверенные
  естественные формулировки корректно переиспользовали категорию `drink`, но это не является
  формальной гарантией для любых будущих сообщений или других моделей.
